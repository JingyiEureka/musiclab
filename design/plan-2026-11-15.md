## C. Moving off the server: static hosting

### C.1 Short answer

Yes, almost. The browser does all the processing; the server does two things:

1. Serves the files. Any static host can do this.
2. `POST /extract-audio/`: ffmpeg pulls the audio out of a video when the
   browser cannot decode it (iPhone Safari with mp4/mov). Static hosting cannot
   run ffmpeg, so this is the one real decision.

Usage evidence: in the 6 days since deploy, `/extract-audio/` was called
**once**, and it failed (400). There were 7 page loads in total.

### C.2 What else changes

- `index.html` uses absolute `/static/...` paths. Making them relative
  (`static/...`) works on both the current server and a GitHub subpath URL.
- GitHub Pages caches every file for 10 minutes; the server currently forces
  revalidation on JS modules. Effect: up to 10 minutes after a deploy a visitor
  may get old files. Acceptable at this traffic.
- HTTPS (needed for `audioWorklet`) comes free with Pages, including on a
  custom domain.
- Removed from the repo: `app/main.py`, `Dockerfile`, `docker-compose.yml`,
  `requirements.txt`, `tests/test_api.py`. Kept: `app/speed_changer.py` and
  `requirements-cli.txt` (offline script, ADR 0011). Local dev becomes
  `python -m http.server` from the repo root.
- New ADR 0012 superseding the "backend keeps static serving and video
  extraction" part of ADR 0001.
